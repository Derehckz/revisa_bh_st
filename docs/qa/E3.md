# QA — Épica E3 — Period lock para interactivo + jobs

## Alcance del cambio
- `lib/period_lock.py`: `PeriodLock`/`PeriodLockError` ahora también evita
  conflictos **dentro del mismo proceso** (dos `PeriodLock` distintos creados
  por el servidor API para el mismo año/mes), vía un registro en memoria
  (`_ACTIVE_LOCKS`) además del archivo `.state/locks/<year>_<month>.lock`. El
  comportamiento entre procesos (main.py, scripts de consola) no cambia.
- `api/interactive/sessions.py`:
  - `create_session(stage_num, params)` adquiere `PeriodLock(year, month,
    script=f"interactive-{stage_num}")` antes de registrar la sesión. Si falla,
    lanza `ValueError` con mensaje claro (el router ya traduce `ValueError` a
    HTTP 409 en `POST /operations/interactive/stages/{stage_num}/sessions`).
  - El lock se guarda en la sesión viva (`session["lock"]`), no se expone en
    `_public_meta`.
  - `cancel_session(...)` libera el lock explícitamente.
  - `update_session_status(...)` libera el lock automáticamente cuando el
    estado pasa a `completed`/`cancelled`/`failed` (cubre además el camino del
    runner).
  - Nueva función `release_session_lock_if_held(session_id)` usada desde
    `api/interactive/runner.py` en un `finally` para blindar la liberación
    ante cualquier salida de `_run_session`.
- `api/operations.py` (`start_stage_job`):
  - Adquiere `PeriodLock(year, month, script=f"job-stage{stage_num}")` después
    de validar prerequisitos y de comprobar que no haya otro job corriendo
    para el período.
  - Si la adquisición falla, propaga `PeriodLockError` (nueva excepción
    distinguible de los `ValueError` de validación).
  - El lock se guarda en un registro interno `_JOB_LOCKS` (por `job_id`, no
    serializado a disco) y se libera en `_run_job` cuando el proceso hijo
    termina (`status` pasa a `success`/`failed`). Si algo falla antes de
    lanzar el hilo, el lock se libera igual (bloque `try/except` alrededor de
    la construcción del job).
- `api/app.py`: `POST /operations/stages/{stage_num}/start` y
  `POST /operations/step0/start` capturan `operations.PeriodLockError` y
  devuelven **HTTP 409** con el mensaje del lock.

## Comportamiento esperado
- Un job y una sesión interactiva para el **mismo período** (año/mes) ya no
  pueden convivir, sin importar si compiten job-vs-job, sesión-vs-sesión o
  job-vs-sesión.
- Períodos distintos nunca se bloquean entre sí.
- Al cancelar/terminar/fallar la operación que tenía el lock, el período queda
  libre de inmediato para la siguiente.

## API
- [ ] `POST /operations/interactive/stages/{n}/sessions` con año/mes ya
      bloqueado por otro job/sesión → HTTP 409 con mensaje claro.
- [ ] `POST /operations/stages/{n}/start` con año/mes ya bloqueado por una
      sesión interactiva → HTTP 409 (antes sería 422 genérico o, peor, corría
      en paralelo).
- [ ] Cancelar la sesión bloqueante (`POST .../sessions/{id}/cancel`) libera
      el período: el siguiente intento ya no da 409.
- [ ] Esperar a que un job termine (`success` o `failed`) libera el período.

## Casos borde
- [ ] Proceso API cae con un job "running": al reiniciar, `_ensure_jobs_loaded`
      marca el job como `failed` (comportamiento previo, sin cambios), pero el
      archivo de lock de disco puede quedar huérfano — se libera con el
      mecanismo existente `break_stale`/`--force-lock` de `main.py`, o se
      libera solo al reiniciar el proceso API (el registro en memoria se
      reinicia).
- [ ] Dos pestañas del navegador intentando iniciar sesiones interactivas
      distintas para el mismo período → la segunda recibe 409 con mensaje
      indicando qué script la está bloqueando.
